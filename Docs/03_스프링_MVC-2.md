# 스프링 MVC 2편

## 타임리프(Thymeleaf) 기본 기능과 레이아웃

### 타임리프의 핵심 특징: SSR과 네추럴 템플릿

타임리프는 백엔드 서버에서 HTML을 동적으로 렌더링하는 **SSR(Server-Side Rendering)** 템플릿 엔진이다. JSP 등 기존 템플릿 엔진과 차별화되는 타임리프만의 가장 강력한 강점은 **네추럴 템플릿(Natural Templates)** 이다.

| 구분 | JSP / 기타 템플릿 엔진 | 타임리프 (Thymeleaf) |
| ------ | ------ | ------ |
| **파일 구조** | HTML 마크업과 서버 스크립틀릿(`<% ... %>`)이 뒤섞임 | 순수 HTML 문법 규격을 그대로 유지 (`th:*` 속성 방식) |
| **로컬 브라우저 실행** | 서버 렌더링 없이 직접 열면 파싱 에러 발생 또는 깨짐 | 웹 브라우저에서 직접 열어도 정상적인 프로토타입 화면 노출 |
| **동적 렌더링 방식** | 서버 엔진을 통해서만 결과 확인 가능 | 웹 브라우저는 알지 못하는 `th:*` 속성을 무시하고 원본 HTML 렌더링 |
| **협업 생산성** | 퍼블리셔와 백엔드 개발자 간 파일 파편화 발생 | 하나의 템플릿 파일로 마크업 검수와 동적 렌더링 동시 해결 |

### 텍스트 출력과 이스케이프(Escape) 매커니즘

HTML 문서는 `<`, `>` 같은 특수 문자를 기반으로 태그를 파싱한다. 사용자가 입력한 데이터에 HTML 특수 문자가 포함되어 있을 때 이를 문자 그대로 안전하게 표현하기 위해 HTML 엔티티로 변환하는 과정을 **이스케이프(Escape)** 라고 한다.

*   `th:text` / `[[...]]` : 기본적으로 이스케이프가 자동 적용된다. `<`는 `&lt;`, `>`는 `&gt;`로 변환되어 악의적인 스크립트 실행(XSS)을 방지한다.
*   `th:utext` / `[(...)]` : 이스케이프를 해제(Unescape)하고 실제 HTML 태그로 해석하여 렌더링한다. (보안상 꼭 필요한 경우에만 제한적으로 사용).

```html
<!-- Controller: model.addAttribute("data", "Hello <b>Spring!</b>"); -->
<ul>
    <li>th:text = <span th:text="${data}"></span></li>      <!-- 출력: Hello &lt;b&gt;Spring!&lt;/b&gt; -->
    <li>th:utext = <span th:utext="${data}"></span></li>    <!-- 출력: Hello <b>Spring!</b> (진하게 렌더링) -->
</ul>
```

### SpringEL 변수식과 스프링 부트 3.0 변경사항

타임리프는 `${...}` 문법을 통해 스프링의 **SpringEL(Spring Expression Language)** 을 완벽하게 지원한다.

*   **Object 프로퍼티 접근** : `${user.username}` -> `${user['username']}` -> `${user.getUsername()}` 프로퍼티 게터 호출.
*   **List 인덱스 접근** : `${users[0].username}` -> `users.get(0).getUsername()`.
*   **Map 키 접근** : `${userMap['userA'].username}` -> `userMap.get("userA").getUsername()`.
*   **지역 변수 선언** : `th:with="first=${users[0]}"` (선언된 태그 내부에서만 유효).

#### 스프링 부트 3.0 (Spring 6.0) 핵심 주의사항

스프링 부트 3.0부터는 보안 및 아키텍처 정비로 인해 타임리프 기본 식 객체인 `${#request}`, `${#response}`, `${#session}`, `${#servletContext}`를 기본 제공하지 않는다.
대신 스프링 부트가 제공하는 **편의 객체**를 사용하여 직관적으로 접근한다:
1.  **HTTP 요청 파라미터 접근** : `${param.paramData}`
2.  **HTTP 세션 데이터 접근** : `${session.sessionData}`
3.  **스프링 빈 직접 접근** : `${@helloBean.hello('Spring!')}`

### 유틸리티 객체와 URL 링크 문법

자바8 날짜 객체(`LocalDate`, `LocalDateTime`)를 다루기 위해 `thymeleaf-extras-java8time` 라이브러리가 기본 통합되어 있으며, `#temporals` 객체를 사용한다.
```html
<!-- 날짜 포맷팅 출력 -->
<span th:text="${#temporals.format(localDateTime, 'yyyy-MM-dd HH:mm:ss')}"></span>
```

#### URL 링크 표현식 `@{...}`
*   **단순 URL** : `@{/hello}` -> `/hello`
*   **쿼리 파라미터** : `@{/hello(param1=${p1}, param2=${p2})}` -> `/hello?param1=data1&param2=data2`
*   **경로 변수(PathVariable)** : `@{/hello/{p1}/{p2}(p1=${p1}, p2=${p2})}` -> `/hello/data1/data2`
*   **경로 변수 + 쿼리 파라미터 조합** : `@{/hello/{p1}(p1=${p1}, param2=${p2})}` -> `/hello/data1?param2=data2`

### 리터럴, 연산자, 그리고 No-Operation
*   **리터럴 대체(Literal Substitutions)** : `|hello ${data}|` 문법을 사용하면 따옴표와 `+` 연산자 결합 없이 템플릿 문자열을 직관적으로 작성할 수 있다.
*   **Elvis 연산자** : `${data}?: '기본값'` (데이터가 null이면 기본값 출력).
*   **No-Operation (`_`)** : `${data}?: _` 연산 결과가 `_`인 경우, 타임리프 태그가 실행되지 않은 것처럼 원본 정적 HTML 태그의 텍스트가 그대로 보존된다.

### 태그 제어와 자바스크립트 인라인

*   `th:classappend` : 기존 클래스 속성에 공백을 두고 자연스럽게 신규 클래스를 추가한다.
*   `th:checked` : HTML 표준 체크박스는 `checked="false"`로 명시되어도 속성이 존재하면 체크된다. 타임리프의 `th:checked`는 값이 `false`이면 HTML의 `checked` 속성 자체를 제거하여 언체크 상태를 유지한다.
*   `th:each="user, userStat : ${users}"` : 반복 루프를 실행하며 상태 객체(`index`, `count`, `size`, `even`, `odd`, `first`, `last`)를 조회할 수 있다.
*   `th:if`, `th:unless` : 조건이 false이면 해당 HTML 태그 자체를 DOM 렌더링에서 제거한다.
*   `<th:block>` : HTML 태그를 생성하지 않고 타임리프 로직(`each`, `if` 등)만 묶어서 실행할 때 사용하는 유일한 자체 가상 태그이다.

#### 자바스크립트 인라인 `<script th:inline="javascript">`

인라인 기능을 적용하면 웹 브라우저 환경에서 발생할 수 있는 스크립트 문법 오류를 완벽히 차단한다:
1.  **문자 타입 자동 인용부호 처리 및 이스케이프** : `var username = "userA";` (`"` 및 특수문자 자동 이스케이프).
2.  **자바스크립트 내추럴 템플릿** : `var username2 = /*[[${user.username}]]*/ "test";` -> 순수 파일로 열면 `"test"`, 서버 렌더링 시 `"userA"`로 대체.
3.  **객체 JSON 자동 직렬화** : `var user = [[${user}]];` -> `var user = {"username":"userA","age":10};` 객체를 JSON 포맷으로 자동 변환.

### 템플릿 조각(Fragment)과 레이아웃 확장

반복되는 헤더, 푸터, 네비게이션 바 등의 공통 UI 코드를 조각으로 모듈화한다.

```
[템플릿 포함 방식 차이]
th:insert="~{template/fragment/footer :: copy}"  -> 현재 태그 내부에 조각을 자식 태그로 삽입
th:replace="~{template/fragment/footer :: copy}" -> 현재 태그 자체를 대상 조각 태그로 완전히 대체
```

#### `<html>` 태그 기반 레이아웃 상속
공통 베이스 레이아웃을 정의하고, 실제 페이지에서는 `<html>` 태그 자체를 `th:replace`로 대체하면서 필요한 타이틀과 섹션 영역만 조각 표현식(`~{::title}`, `~{::link}`, `~{::section}`)으로 파라미터 전달하여 화면을 조립하는 방식을 실무에서 널리 활용한다.

## 타임리프 스프링 통합과 폼 처리

### 스프링 폼 연동의 핵심: `th:object`와 `th:field`

스프링 MVC와 타임리프가 결합하면 HTML Form 데이터를 모델 객체와 양방향으로 바인딩하는 작업이 극적으로 단순화된다.

*   `th:object="${item}"` : `<form>` 태그 내부에서 사용할 커맨드 객체를 지정한다.
*   `*{itemName}` : 선택 변수 식(Asterisk syntax)으로, 부모 태그에 지정된 `th:object`의 내부 프로퍼티를 가리킨다.
*   `th:field="*{itemName}"` : HTML 엘리먼트의 `id`, `name`, `value` 속성을 한 번에 자동 생성한다.
    *   `id` : 필드명과 동일하게 자동 생성 (`id="itemName"`)
    *   `name` : 필드명과 동일하게 자동 생성 (`name="itemName"`)
    *   `value` : 모델 객체의 현재 프로퍼티 값을 자동으로 채움 (`value="기존값"`)

```html
<!-- 타임리프 작성 코드 -->
<form th:action th:object="${item}" method="post">
    <input type="text" th:field="*{itemName}" class="form-control">
</form>

<!-- 브라우저에 렌더링된 최종 HTML -->
<form action="" method="post">
    <input type="text" id="itemName" name="itemName" value="itemA" class="form-control">
</form>
```

### 단인 체크박스와 히든 필드(`_open`) 트릭

HTML 표준 체크박스는 선택되지 않았을 때 클라이언트 브라우저가 해당 필드의 key 자체를 서버로 전송하지 않는다.

```
[HTML 표준 체크박스의 결함]
1. 체크 상태 전송    : open=on  -> 스프링이 Boolean true로 정상 바인딩
2. 체크 해제 상태 전송: (전송 데이터 없음) -> 스프링 모델 객체의 open 필드는 null로 남음
3. 문제점: 수정 화면에서 기존 true이던 값을 체크 해제하여 저장해도, 서버는 null을 수신하여 변경 의도를 알 수 없음!
```

#### 스프링 MVC의 언더스코어(`_`) 히든 필드 규격

스프링 MVC는 체크 해제를 감지하기 위해 기존 필드명 앞에 언더스코어를 붙인 히든 필드를 전송하는 규격을 사용한다.
*   `<input type="hidden" name="_open" value="on"/>`
*   **체크 시** : `open=on&_open=on` 전송 -> 스프링이 `open` 값을 인식하여 `true` 주입 (`_open` 무시).
*   **체크 해제 시** : `_open=on`만 전송 -> 스프링이 `open` 값이 넘어오지 않은 것을 인지하고 명시적으로 `false` 주입.
*   **타임리프 자동화** : `<input type="checkbox" th:field="*{open}"/>`를 선언하면 타임리프가 히든 필드 `<input type="hidden" name="_open" value="on"/>`을 자동으로 생성해주어 실수를 원천 방지한다.

### 멀티 체크박스, 라디오 버튼, 셀렉트 박스 컴포넌트

#### 1. 멀티 체크박스와 `#ids.prev()`

동일한 name을 가진 다중 체크박스를 루프로 생성할 때, HTML 태그의 `id`는 고유해야 하므로 타임리프는 `regions1`, `regions2`, `regions3` 형태로 번호를 자동 부여한다.
따라서 `<label>`의 `for` 속성을 맞추기 위해 `#ids.prev('regions')` 유틸리티 함수를 사용한다.

```html
<div th:each="region : ${regions}" class="form-check form-check-inline">
    <input type="checkbox" th:field="*{regions}" th:value="${region.key}" class="form-check-input">
    <label th:for="${#ids.prev('regions')}" th:text="${region.value}" class="form-check-label">서울</label>
</div>
```

#### 2. 라디오 버튼 (ENUM 활용)

라디오 버튼은 필수 선택 구조이거나 기존 선택을 해제할 수 없으므로 언더스코어 히든 필드가 필요하지 않다.
타임리프는 `th:field`의 값과 `th:value`를 비교하여 일치하는 항목에 `checked="checked"`를 자동 부여한다.

#### 3. 셀렉트 박스 (Select Box)

자바 객체 리스트나 컬렉션을 기반으로 `<option>` 태그를 반복 생성하며, 선택된 코드와 모델 값이 일치하면 `selected="selected"`를 자동 추가한다.

#### `@ModelAttribute`를 활용한 공통 데이터 자동 바인딩
등록 폼, 수정 폼, 조회 폼에서 반복적으로 사용되는 등록 지역, 배송 방식, 상품 종류와 같은 공통 참조 데이터를 모든 컨트롤러 메서드마다 `model.addAttribute()`로 중복 작성하는 것을 방지하기 위해 메서드 레벨 `@ModelAttribute`를 선언한다.

```java
@Controller
public class ItemController {
    
    // 해당 컨트롤러의 모든 요청 메서드 실행 시 model.addAttribute("regions", ...)가 자동 수행됨
    @ModelAttribute("regions")
    public Map<String, String> regions() {
        Map<String, String> regions = new LinkedHashMap<>();
        regions.put("SEOUL", "서울");
        regions.put("BUSAN", "부산");
        regions.put("JEJU", "제주");
        return regions;
    }
}
```

## 메시지와 국제화(i18n)

### 메시지 중앙 관리와 국제화의 필요성

웹 애플리케이션의 모든 화면에 하드코딩된 레이블, 버튼 명칭, 오류 문구는 기획 변경 시 수십 개의 HTML 파일을 일일이 수정해야 하는 유지보수 병목을 유발한다.
또한 글로벌 서비스를 위해서는 접속 클라이언트의 언어 설정에 맞추어 화면 문구를 동적으로 분기해야 한다.

```
[메시지 및 국제화 파일 분리 구조]
/resources/messages.properties      -> 기본 메시지 파일 (한글 기본)
/resources/messages_en.properties   -> 영어권 사용자 전용 메시지 파일
/resources/errors.properties         -> 검증 오류 전용 메시지 파일
```

### 스프링 부트 `MessageSource` 설정과 타임리프 `#{...}`

스프링 부트는 `ResourceBundleMessageSource`를 `MessageSource` 빈으로 자동 등록한다.
`application.properties`에 다음과 같이 베이스 파일명을 등록하여 사용한다:

```properties
spring.messages.basename=messages,errors
```

*   **타임리프 메시지 표현식** : `#{...}` 문법을 사용하여 프로퍼티 키를 조회한다.
    *   `<label th:text="#{label.item.itemName}">상품명</label>`
*   **파라미터 치환 지원** :
    *   프로퍼티 정의: `hello.name=안녕 {0}`
    *   타임리프 호출: `<p th:text="#{hello.name(${item.itemName})}"></p>`
    *   자바 코드 호출: `messageSource.getMessage("hello.name", new Object[]{"Spring"}, Locale.KOREA);`

### 국제화 동작 원리와 `LocaleResolver`
스프링은 클라이언트가 요청 시 전송하는 HTTP 요청 헤더 `Accept-Language`를 분석하여 최적의 언어 파일을 자동 선택한다.

```
[스프링 국제화 파일 선택 탐색 순서 (예: Locale이 en_US인 경우)]
1. messages_en_US.properties 탐색
2. 없으면 messages_en.properties 탐색
3. 없으면 디폴트 messages.properties 사용
```

*   **`LocaleResolver` 인터페이스** : 클라이언트의 로케일을 결정하는 스프링 추상화 인터페이스이다.
    *   기본 구현체: `AcceptHeaderLocaleResolver` (HTTP 헤더 기반 탐색).
    *   커스텀 확장: 사용자가 웹 화면에서 직접 언어(한국어/영어)를 셀렉트 박스로 변경하는 경우, 쿠키(`CookieLocaleResolver`) 또는 세션(`SessionLocaleResolver`) 기반 구현체로 교체하여 영속적인 언어 선택을 지원한다.

## 검증(Validation) 1 - BindingResult와 오류 코드 설계

### 직접 검증(`Map<String, String> errors`)의 한계
컨트롤러 내부에서 `if` 문으로 검증하여 `Map`에 에러를 담아 넘기는 원시적인 방식은 치명적인 결함이 있다:
1.  **타입 변환 오류 처리 불가** : `Integer price` 필드에 사용자가 문자 "A"를 입력하면, 스프링 MVC가 모델 객체에 값을 바인딩하는 시점에 `MethodArgumentTypeMismatchException`이 발생하여 **컨트롤러 진입 자체가 차단되고 400 오류 페이지가 호출**된다.
2.  **사용자 입력 데이터 유실** : 타입이 맞지 않으므로 모델에 값을 담을 수 없고, 사용자가 입력했던 오타 문자열이 화면에서 완전히 증발하여 재입력 경험을 크게 해친다.
3.  **뷰 템플릿의 검증 출력 코드 중복** : 매 폼마다 필드 오류 검증 태그가 방대하게 늘어난다.

### 스프링 검증의 핵심: `BindingResult`
`BindingResult`는 스프링이 제공하는 검증 오류 보관 인터페이스(`Errors` 상속)이다.

```
[BindingResult의 핵심 역할]
1. @ModelAttribute 객체 바로 뒤에 선언 시, 데이터 바인딩 오류(타입 오류 등)가 발생해도
   예외로 튕겨 나가지 않고 오류 정보(FieldError)를 BindingResult에 적재한 후 컨트롤러를 정상 호출한다!
2. 검증 실패 시 모델(Model)에 자동으로 담겨 뷰 템플릿으로 투명하게 전달된다.
```

> [!WARNING]
> **파라미터 위치 제약** : `BindingResult`는 반드시 검증할 대상 객체(`@ModelAttribute Item item`)의 **바로 다음 파라미터 위치**에 선언해야 한다. 순서가 어긋나면 대상 타겟을 찾지 못해 정상 동작하지 않는다.

### `FieldError`와 사용자 입력값 보존(`rejectedValue`)
타입 변환 오류나 비즈니스 검증 실패 시 사용자가 입력한 잘못된 값을 유지하기 위해 `FieldError`의 확장 생성자를 사용한다.

```java
public FieldError(String objectName, String field, @Nullable Object rejectedValue, 
                  boolean bindingFailure, @Nullable String[] codes, 
                  @Nullable Object[] arguments, @Nullable String defaultMessage)
```
*   `rejectedValue` : 사용자가 입력했던 거절된 값(문자열 등)을 그대로 보관한다.
*   `bindingFailure` : 타입 변환 바인딩 실패 여부 (`true`/`false`).
*   **타임리프 뷰의 복원 마법** : 화면 렌더링 시 `th:field`는 모델 객체의 정상 값 대신 `FieldError`에 저장된 `rejectedValue`를 우선적으로 꺼내어 input 태그의 value로 출력한다.

```html
<!-- 타임리프 스프링 검증 통합 태그 -->
<div th:if="${#fields.hasGlobalErrors()}">
    <p class="field-error" th:each="err : ${#fields.globalErrors()}" th:text="${err}">글로벌 오류</p>
</div>

<input type="text" id="price" th:field="*{price}" th:errorclass="field-error" class="form-control">
<div class="field-error" th:errors="*{price}">가격 오류 메시지</div>
```

### 축약 메서드 `rejectValue()`와 `MessageCodesResolver`

매번 복잡한 `FieldError` 생성자를 호출하는 대신 `bindingResult.rejectValue()`를 호출하면 간결해진다:

```java
bindingResult.rejectValue("price", "range", new Object[]{1000, 1000000}, null);
bindingResult.reject("totalPriceMin", new Object[]{10000, resultPrice}, null);
```

#### `MessageCodesResolver`의 계층적 오류 메시지 생성 규칙
스프링은 `DefaultMessageCodesResolver`를 통해 단순한 오류 코드(`range`)를 바탕으로 구체적인 메시지에서 범용적인 메시지로 단계별 메시지 키 목록을 자동 생성한다.

| 구분 | 단계 (우선순위 순) | 생성 규칙 | 예시 (`price` 필드에 `range` 코드) |
| ------ | ------ | ------ | ------ |
| **객체 오류** | 1순위 (구체적) | `code + "." + object name` | `totalPriceMin.item` |
| | 2순위 (범용적) | `code` | `totalPriceMin` |
| **필드 오류** | 1순위 (가장 구체적) | `code + "." + object name + "." + field` | `range.item.price` |
| | 2순위 | `code + "." + field` | `range.price` |
| | 3순위 | `code + "." + field type` | `range.java.lang.Integer` |
| | 4순위 (가장 범용적) | `code` | `range` |

#### 오류 코드 설계 전략: "구체적인 것에서 덜 구체적인 것으로"
*   중요한 비즈니스 필드는 Level 1(`range.item.price`)로 상세한 전용 문구를 등록한다.
*   공통적인 규칙은 Level 4(`range={0} ~ {1} 범위를 허용합니다.`)로 등록해두면, 개별 메시지를 일일이 정의하지 않아도 기본 메시지로 자동 fallback 되어 유지보수성이 극대화된다.
*   **스프링 기본 타입 오류(`typeMismatch`) 대응** : 숫자에 문자를 입력하면 스프링이 `typeMismatch` 오류 코드를 자동 생성하므로, `errors.properties`에 `typeMismatch.java.lang.Integer=숫자를 입력해주세요.` 한 줄만 추가하면 자바 코드를 단 한 줄도 손대지 않고 깔끔한 사용자 오류 메시지를 띄울 수 있다.

### `Validator` 인터페이스 분리와 `@Validated`
컨트롤러 내부에 비즈니스 로직과 비대한 검증 코드가 공존하는 문제를 해결하기 위해 스프링 `Validator` 인터페이스로 역할을 분리한다.

```java
@Component
public class ItemValidator implements Validator {
    @Override
    public boolean supports(Class<?> clazz) {
        return Item.class.isAssignableFrom(clazz);
    }

    @Override
    public void validate(Object target, Errors errors) {
        Item item = (Item) target;
        ValidationUtils.rejectIfEmptyOrWhitespace(errors, "itemName", "required");
        if (item.getPrice() == null || item.getPrice() < 1000 || item.getPrice() > 1000000) {
            errors.rejectValue("price", "range", new Object[]{1000, 1000000}, null);
        }
        // ...
    }
}
```

*   `@InitBinder`와 `WebDataBinder` : 컨트롤러에 바인더를 등록하면 컨트롤러 호출 시마다 자동 검증을 수행할 수 있다.
*   컨트롤러 파라미터에 `@Validated`를 선언하면 바인더에 등록된 검증기의 `supports()`를 거쳐 `validate()`가 자동 호출된다.

## 검증(Validation) 2 - Bean Validation과 실무 폼 객체 분리

### Bean Validation 표준과 스프링 부트 자동 통합
검증 로직을 매번 코드로 작성하는 번거로움을 없애기 위해 표준 애노테이션으로 검증 규칙을 선언하는 기술이 **Bean Validation(JSR-380)** 이며, 사실상의 표준 구현체는 **하이버네이트 Validator(Hibernate Validator)** 이다.

*   `@NotBlank` : null, 빈 문자열(`""`), 공백만 있는 문자열(`" "`)을 모두 불허.
*   `@NotNull` : null 불허.
*   `@Range(min = 1000, max = 1000000)` : 범위 검증.
*   `@Max(9999)` : 최대치 제한.

#### 스프링 부트의 검증기 자동 등록
`spring-boot-starter-validation` 라이브러리를 추가하면 스프링 부트는 `LocalValidatorFactoryBean`을 글로벌 Validator로 자동 등록한다.
개발자는 파라미터에 `@Valid`(자바 표준) 또는 `@Validated`(스프링 전용)만 명시하면 된다.

#### Bean Validation 검증 2단계 순서

1.  **1단계: 바인딩 시도** : `@ModelAttribute`의 각 필드에 대해 타입 변환을 시도한다. 실패 시 `typeMismatch` 오류를 `BindingResult`에 적재한다.
2.  **2단계: 검증 수행** : **타입 바인딩에 성공한 정상 필드에 대해서만** Bean Validation 애노테이션 검증을 실행한다. (타입 자체가 맞지 않는 필드는 검증이 무의미하므로 검증기를 실행하지 않는다).

### 오브젝트 오류(글로벌 오류)의 실무적 처리

특정 단일 필드를 넘어선 복합 조건(예: `price * quantity >= 10000`) 검증을 위해 Bean Validation은 `@ScriptAssert` 애노테이션을 제공하지만, 실제 자바 17+ 환경 제약, 복잡도, 타 시스템 및 DB 연동 검증의 한계로 실무에서는 거의 사용하지 않는다.
*   **실무 권장 패턴** : 필드 검증은 애노테이션에 맡기고, 오브젝트 오류는 컨트롤러 내부나 서비스 계층에서 순수 자바 코드로 검증 후 `bindingResult.reject("totalPriceMin", ...)`을 직접 호출하는 것이 훨씬 유연하고 유지보수에 유리하다.

### 등록과 수정의 검증 요구사항 충돌과 `groups`의 한계
*   **등록 요구사항** : 상품 ID(`id`) 없음, 수량(`quantity`) 최대 9,999개 제한.
*   **수정 요구사항** : 상품 ID(`id`) 필수(`@NotNull`), 수량(`quantity`) 제한 없음.

도메인 객체 `Item` 하나에 검증 애노테이션을 몰아넣으면 등록 시 `id`가 null이라 검증이 터지고, 수정 시 수량 제한을 풀 수 없는 모순이 발생한다.
이를 해결하기 위해 Bean Validation은 `groups` 기능(`@Validated(SaveCheck.class)`)을 제공하지만, 엔티티 코드가 심각하게 지저분해지고 복잡도가 증가하여 실무에서는 거의 사용하지 않는다.

### 실무 정석: Form 전송 객체(DTO) 분리
실무에서는 화면에서 전달되는 데이터가 도메인 엔티티(`Item`)와 1:1로 일치하는 경우가 거의 없다. 회원 가입 시 약관 동의, 부가 정보 등이 함께 전달되므로, 전송 데이터 전용 DTO를 엄격히 분리한다.

```
[Form 객체 분리 아키텍처 흐름]
1. 등록: HTML Form -> ItemSaveForm(전용 검증) -> Controller -> Item 도메인 엔티티 변환 -> Repository
2. 수정: HTML Form -> ItemUpdateForm(전용 검증) -> Controller -> Item 도메인 엔티티 변환 -> Repository
```

```java
// 저장 전용 폼 객체
@Data
public class ItemSaveForm {
    @NotBlank
    private String itemName;
    @NotNull
    @Range(min = 1000, max = 1000000)
    private Integer price;
    @NotNull
    @Max(value = 9999)
    private Integer quantity;
}
```

```java
@PostMapping("/add")
public String addItem(@Validated @ModelAttribute("item") ItemSaveForm form, 
                      BindingResult bindingResult, 
                      RedirectAttributes redirectAttributes) {
    if (bindingResult.hasErrors()) {
        return "validation/v4/addForm";
    }
    // 성공 시 폼 객체 데이터를 도메인 엔티티로 변환
    Item item = new Item(form.getItemName(), form.getPrice(), form.getQuantity());
    Item savedItem = itemRepository.save(item);
    // ...
}
```

> [!WARNING]
> `@ModelAttribute("item")` 이름 명시** : 이름을 생략하면 클래스명 규칙에 따라 모델에 `itemSaveForm`으로 담기게 되어 기존 타임리프 뷰의 `th:object="${item}"`와 불일치가 발생하므로, 명시적으로 `"item"` 이름을 지정해야 뷰 템플릿의 수정을 최소화할 수 있다.

### `@ModelAttribute` vs `@RequestBody` 검증 동작 비교

| 구분 | `@ModelAttribute` (Form / QueryParam) | `@RequestBody` (API JSON) |
| ------ | ------ | ------ |
| **처리 주체** | `ModelFactory`, `WebDataBinder` | `HttpMessageConverter` (MappingJackson2...) |
| **바인딩 단위** | **필드 단위(Field-by-Field)** 로 세밀하게 적용 | **메시지 바디 전체(Object-Level)** 단위로 한 번에 역직렬화 |
| **타입 변환 실패 시** | 오류 필드만 `FieldError` 적재, **나머지 필드는 정상 바인딩 및 Validator 검증 진행** | **JSON 파싱 자체가 실패하여 컨트롤러 진입 차단 (400 Bad Request)**, **Validator 미실행** |
| **적용 시점** | 필드 바인딩 완료 후 `@Valid` 검증 실행 | JSON -> 객체 역직렬화 성공 후에만 `@Valid` 검증 실행 |

## 로그인 처리 1 - 쿠키, 세션과 보안 아키텍처

### HTTP Stateless 환경과 쿠키 기반 인증의 치명적 취약점
HTTP는 상태를 유지하지 않는 무상태(Stateless) 프로토콜이다. 로그인 상태를 유지하기 위해 서버가 로그인 성공 응답 시 쿠키(`Set-Cookie: memberId=1`)를 발급하고 브라우저가 이후 요청마다 쿠키를 전송하는 방식을 취할 수 있으나, 심각한 보안 결함이 발생한다.

```
[쿠키 기반 인증의 3대 보안 취약점]
1. 쿠키 값 변조 위협 : 클라이언트 개발자 도구에서 memberId=2로 쿠키 값을 임의 변경하면 타인의 계정으로 즉시 로그인됨
2. 쿠키 탈취 위협   : 로컬 PC 해킹이나 네트워크 패킷 스니핑을 통해 쿠키가 노출되면 영구적으로 악용 가능
3. 영구 위협       : 한 번 노출된 쿠키는 서버 차원에서 무효화할 수단이 없음
```

### 세션(Session) 기반 인증 메커니즘
민감한 회원 정보와 권한 정보는 오직 안전한 **서버 메모리(세션 저장소)** 에만 보관하고, 클라이언트와 서버 간에는 예측 불가능한 임의의 토큰(UUID)만을 주고받도록 설계한다.

```
[세션 동작 원리]
1. 클라이언트: 로그인 ID/PW 전송
2. 서버: 회원 인증 성공 후, 추정 불가능한 UUID 세션 ID 생성 (예: 7b3f9...-4a1c)
3. 서버: 세션 저장소에 [sessionId -> Member 객체] 매핑 저장
4. 서버: 클라이언트에 Set-Cookie: mySessionId=7b3f9...-4a1c 응답 (민감 정보 완전 은닉)
5. 클라이언트: 이후 요청마다 mySessionId 쿠키 전달
6. 서버: 세션 저장소에서 UUID로 회원 정보 역조회하여 로그인 상태 확인
```

### 서블릿 `HttpSession`과 스프링 편의 애노테이션
서블릿 컨테이너는 표준 세션 기술인 `HttpSession`을 제공하며, 클라이언트에 `JSESSIONID`라는 이름의 쿠키를 발행한다.

```java
// 로그인 처리: getSession() 기본값은 true (세션이 없으면 신규 생성)
HttpSession session = request.getSession();
session.setAttribute(SessionConst.LOGIN_MEMBER, loginMember);

// 로그아웃 처리: 세션 무효화
HttpSession session = request.getSession(false); // 세션 없으면 null 반환
if (session != null) {
    session.invalidate();
}
```

#### 스프링 `@SessionAttribute`를 통한 초간결 세션 조회
```java
@GetMapping("/")
public String homeLogin(
        @SessionAttribute(name = SessionConst.LOGIN_MEMBER, required = false) Member loginMember, 
        Model model) {
    if (loginMember == null) {
        return "home";
    }
    model.addAttribute("member", loginMember);
    return "loginHome";
}
```

### 세션 유지 정책과 타임아웃(Timeout) 설정
*   **URL jsessionid 노출 방지** : 브라우저 최초 접근 시 쿠키 지원 여부를 알 수 없어 URL 끝에 `;jsessionid=...`가 붙는 현상을 방지하기 위해 쿠키 전용 모드로 고정한다:
    ```properties
    server.servlet.session.tracking-modes=cookie
    ```
*   **세션 타임아웃 전략** : 사용자가 로그아웃 버튼을 누르지 않고 브라우저를 닫는 경우 세션 메모리가 무한정 누적되어 OOM(Out Of Memory)이 발생할 수 있다.
    *   스프링 부트는 사용자의 마지막 HTTP 요청 시점(`LastAccessedTime`)을 기준으로 **30분(1800초)** 동안 추가 요청이 없으면 WAS가 세션을 자동 삭제하도록 기본 관리한다.
    ```properties
    server.servlet.session.timeout=1800
    ```

## 로그인 처리 2 - 웹 공통 관심사(서블릿 필터와 스프링 인터셉터)

### 웹 공통 관심사(Cross-cutting Concern)의 문제

로그인 체크, URL 접근 권한 검증, 전역 요청 로깅 등 웹 애플리케이션 전반에 걸친 공통 로직을 개별 컨트롤러마다 삽입하면 중복이 발생하고 누락 위험이 커진다.
스프링 AOP를 적용할 수도 있지만, 웹 관련 공통 관심사는 HTTP 요청 헤더, 쿠키, 세션, URL 패턴 정보 등 `HttpServletRequest`와 서블릿 환경에 밀접하게 결합되어 있으므로 **서블릿 필터**나 **스프링 인터셉터**를 사용하는 것이 정석이다.

### 서블릿 필터(Servlet Filter)

서블릿 컨테이너가 제공하는 기술로, 디스패처 서블릿 이전에 호출된다.

```
[서블릿 필터 요청 흐름]
HTTP 요청 -> WAS -> 필터1 -> 필터2 -> 디스패처 서블릿 -> 컨트롤러
```

*   `doFilter(ServletRequest request, ServletResponse response, FilterChain chain)` : 핵심 필터 메서드로, 다음 필터나 서블릿을 호출하기 위해 **`chain.doFilter(request, response)`를 반드시 호출**해야 한다. 호출하지 않으면 요청이 그 자리에서 중단된다.
*   **화이트리스트(Whitelist) 패턴** : 홈 화면, 회원가입, 로그인 등 비인증 접근을 허용할 URL 목록을 정의하고, 미인증 사용자 요청 시 `httpResponse.sendRedirect("/login?redirectURL=" + requestURI)`로 튕겨내고 `return;`으로 종료한다.

### 스프링 인터셉터(Spring Interceptor)
스프링 MVC 프레임워크가 제공하는 기술로, 디스패처 서블릿과 컨트롤러(핸들러) 사이에 위치한다.

```
[스프링 인터셉터 요청 흐름]
HTTP 요청 -> WAS -> 필터 -> 디스패처 서블릿 -> preHandle -> 컨트롤러(핸들러) -> postHandle -> View -> afterCompletion
```

#### 인터셉터의 3단계 라이프사이클 메서드

```java
public interface HandlerInterceptor {
    default boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception;
    default void postHandle(HttpServletRequest request, HttpServletResponse response, Object handler, @Nullable ModelAndView modelAndView) throws Exception;
    default void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, @Nullable Exception ex) throws Exception;
}
```

```
[예외 발생 시 인터셉터 동작 차이 (매우 중요)]
1. preHandle       : 핸들러 호출 전 실행. false 반환 시 컨트롤러 미호출 및 중단.
2. postHandle      : 컨트롤러 정상 반환 후 실행. 컨트롤러에서 예외가 발생하면 호출되지 않음!
3. afterCompletion : 뷰 렌더링 후 실행. 예외가 발생하든 안 하든 무조건 호출됨을 보장 (공통 예외 로깅 및 리소스 정리 전담).
```

### 서블릿 필터 vs 스프링 인터셉터 1:1 비교

| 비교 항목 | 서블릿 필터 (Servlet Filter) | 스프링 인터셉터 (Spring Interceptor) |
| ------ | ------ | ------ |
| **관리 주체** | 서블릿 컨테이너 (Tomcat 등) | 스프링 컨테이너 (스프링 MVC 프레임워크) |
| **호출 위치** | WAS와 디스패처 서블릿 사이 | 디스패처 서블릿과 컨트롤러(핸들러) 사이 |
| **스프링 빈 등록** | `FilterRegistrationBean` 사용 | `WebMvcConfigurer.addInterceptors()` 등록 |
| **URL 패턴 문법** | 서블릿 단순 URL 패턴 (`/*`) | 스프링의 정밀한 `PathPattern` (`/**`, `excludePathPatterns`) |
| **전달 파라미터** | `ServletRequest`, `ServletResponse` 단순 제공 | `handler`(호출 대상 메서드 정보), `ModelAndView`, 발생 `Exception` 객체 |
| **실무 사용 권장** | 보안 프레임워크, 인코딩 변환 등 전역 서블릿 계층 작업 | **웹 애플리케이션의 일반적인 로깅, 인증/인가 검증 (인터셉터 압도적 권장)** |

### 정밀한 URL 제어: PathPattern과 인터셉터 등록

인터셉터는 체인 구성이 간결하며, 특정 경로를 제외(`excludePathPatterns`)하는 설정이 매우 강력하다.

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LoginCheckInterceptor())
                .order(1)
                .addPathPatterns("/**") // 전체 적용
                .excludePathPatterns("/", "/members/add", "/login", "/logout", "/css/**", "/*.ico", "/error"); // 제외 경로
    }
}
```

### `ArgumentResolver`를 활용한 커스텀 `@Login` 애노테이션

세션에서 회원 정보를 매번 조회하는 보일러플레이트 코드를 제거하기 위해 `HandlerMethodArgumentResolver`를 구현하여 컨트롤러 파라미터에 유저 도메인 객체를 다이렉트로 주입한다.

```java
// 1. 커스텀 애노테이션 정의
@Target(ElementType.PARAMETER)
@Retention(RetentionPolicy.RUNTIME)
public @interface Login {}

// 2. ArgumentResolver 구현
public class LoginMemberArgumentResolver implements HandlerMethodArgumentResolver {
    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        boolean hasLoginAnnotation = parameter.hasParameterAnnotation(Login.class);
        boolean hasMemberType = Member.class.isAssignableFrom(parameter.getParameterType());
        return hasLoginAnnotation && hasMemberType;
    }

    @Override
    public Object resolveArgument(MethodParameter parameter, ModelAndViewContainer mavContainer, 
                                  NativeWebRequest webRequest, WebDataBinderFactory binderFactory) {
        HttpServletRequest request = (HttpServletRequest) webRequest.getNativeRequest();
        HttpSession session = request.getSession(false);
        if (session == null) return null;
        return session.getAttribute(SessionConst.LOGIN_MEMBER);
    }
}

// 3. 컨트롤러 사용: 놀라울 정도로 깔끔해진 파라미터
@GetMapping("/")
public String homeLogin(@Login Member loginMember, Model model) {
    if (loginMember == null) return "home";
    model.addAttribute("member", loginMember);
    return "loginHome";
}
```
