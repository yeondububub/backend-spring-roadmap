# 스프링 MVC 1편

## 웹 애플리케이션의 기초와 서블릿의 탄생

### 웹 서버(Web Server) vs 웹 애플리케이션 서버(WAS)

현대 웹 아키텍처의 모든 통신은 **HTTP(HyperText Transfer Protocol)**를 기반으로 동작한다. HTML, 텍스트, 이미지, 영상, 파일은 물론 JSON, XML 형태의 REST API 데이터까지 모든 형태의 데이터가 HTTP 메시지에 실려 전송된다.


| 구분 | 웹 서버 (Web Server) | 웹 애플리케이션 서버 (WAS) |
| :--- | :--- | :--- |
| **주요 역할** | HTTP 기반의 정적 리소스 제공 | 프로그램 코드를 실행하여 동적 비즈니스 로직 수행 |
| **제공 리소스** | 정적 HTML, CSS, JavaScript, 이미지, 파일 등 | 동적 HTML 렌더링, HTTP API(JSON) 응답 |
| **대표 제품** | NGINX, APACHE | 톰캣(Tomcat), Jetty, Undertow |
| **핵심 특성** | 프로그램 실행 기능이 없거나 제한적이며 가볍고 안정적 | 서블릿 컨테이너를 내장하여 자바 애플리케이션 로직 실행 전담 |

#### WEB - WAS - DB 3티어 아키텍처 구성의 이유

WAS 하나만으로도 정적 리소스와 동적 로직을 모두 처리할 수 있지만, 실무에서는 일반적으로 **Web Server - WAS - DB**의 3계층 구조를 구성된다.

1. **서버 과부하 방지 및 리소스 최적화**: 가장 비싼 자원인 애플리케이션 비즈니스 로직 처리가 정적 파일 다운로드 요청 때문에 지연되는 현상을 원천 방지한다. 정적 요청이 늘어나면 Web Server를 증설하고, 비즈니스 트래픽이 몰리면 WAS를 증설할 수 있다.
2. **장애 격리**: 로직 오류나 메모리 누수로 WAS나 DB에 장애가 발생하더라도, 앞단의 Web Server는 살아있으므로 사용자에게 친절한 "서비스 점검 중" 오류 안내 페이지를 즉각 노출할 수 있다.

### 서블릿(Servlet)이 해결해 준 핵심 문제

서블릿 컨테이너가 없다면, 개발자는 클라이언트와의 저수준 통신을 위해 다음 작업을 직접 구현해야 한다.

- 서버 TCP/IP 소켓 연결 대기 및 커넥션 생성
- HTTP 요청 메시지 파싱 (HTTP 메서드, URL, 헤더, 메시지 바디 등)
- Content-Type 확인 및 POST 바디 파라미터 파싱
- HTTP 응답 시작 라인, 헤더 규격 조립
- 메시지 바디에 HTML 또는 데이터 작성
- TCP/IP 소켓 응답 전달 및 연결 종료

**서블릿(Servlet)** 을 지원하는 WAS를 사용하면 위와 같이 반복적이고 복잡한 네트워크 통신 처리를 WAS가 완전히 자동화한다.  
개발자는 오직 의미 있는 비즈니스 로직에만 집중할 수 있게 된다.

### 멀티 쓰레드와 쓰레드 풀(Thread Pool)

* **쓰레드(Thread)**: 애플리케이션 코드를 하나하나 순차적으로 실행하는 주체이다.
* **요청당 쓰레드 생성(Thread per request) 방식의 한계**:
  * 동시 요청이 올 때마다 쓰레드를 새로 생성하면, 쓰레드 생성/종료 비용(CPU/메모리)이 과도하게 발생하고 컨텍스트 스위칭 오버헤드가 급증한다.
  * 트래픽이 폭증할 경우 쓰레드 생성 한계를 초과하여 서버 전체가 다운된다.
* **쓰레드 풀(Thread Pool) 메커니즘**:
  * 미리 정해진 수(톰캣 기본 200개)의 쓰레드를 풀에 만들어두고, 요청이 들어오면 유휴 쓰레드를 대여한 뒤 처리가 끝나면 반납받는다.
  * 쓰레드가 모두 소진되면 대기 큐에서 대기시키거나 거절하여 서버 다운을 방지하고 빠른 응답 속도를 유지한다.
* **싱글톤(Singleton)과 무상태(Stateless) 설계의 절대적 중요성**:
  * 서블릿 컨테이너는 메모리 절약과 생성 오버헤드 방지를 위해 **서블릿 객체를 단 하나만 생성하는 싱글톤으로 관리**한다.
  * 수많은 쓰레드가 동일한 서블릿 인스턴스에 동시 접근하므로, 서블릿 클래스 내부에는 **상태를 유지하는 공유 필드를 절대로 선언해서는 안 되며**, 지역 변수나 파라미터를 활용해 철저히 무상태(Stateless)로 설계해야 한다.

### SSR(Server-Side Rendering) vs CSR(Client-Side Rendering)

* **SSR (서버 사이드 렌더링)**: 서버에서 최종 완성된 HTML을 생성하여 브라우저로 내려주는 방식이다 (예: JSP, 타임리프). 정적인 콘텐츠 표현에 적합하며 초기 로딩 속도와 SEO(검색엔진 최적화)에 유리하다.
* **CSR (클라이언트 사이드 렌더링)**: 서버는 빈 HTML 껍데기와 JavaScript 링크, 그리고 순수 데이터(JSON)만 제공하고, 웹 브라우저 내의 JavaScript 프레임워크(React, Vue.js)가 동적으로 화면을 렌더링하는 방식이다.

## 서블릿 핵심 동작 원리와 HTTP 요청·응답 데이터 처리

### 서블릿 환경 구성과 스프링 부트 3.0 변경사항

스프링 부트는 톰캣 서버를 내장하고 있으며, `@ServletComponentScan`을 통해 패키지 내 서블릿을 탐색하여 자동 등록한다.

```java
@ServletComponentScan // 서블릿 자동 등록
@SpringBootApplication
public class ServletApplication {
    public static void main(String[] args) {
        SpringApplication.run(ServletApplication.class, args);
    }
}
```

> **스프링 부트 3.0 (Spring Framework 6.0) 핵심 주의사항**:
> 1. **Java 17 이상** 필수 사용.
> 2. 자바 라이선스 문제로 서블릿 패키지가 `javax.servlet`에서 `jakarta.servlet`으로 변경되었다 (`HttpServletRequest`, `HttpServletResponse` 포함).

### 서블릿 기본 구조와 HttpServletRequest

```java
@WebServlet(name = "helloServlet", urlPatterns = "/hello")
public class HelloServlet extends HttpServlet {
    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        String username = request.getParameter("username");
        
        response.setContentType("text/plain");
        response.setCharacterEncoding("utf-8");
        response.getWriter().write("hello " + username);
    }
}
```
* **`HttpServletRequest`의 주요 역할**:
  1. **HTTP 요청 메시지 파싱 결과 제공**: Start-line(메서드, URL, 프로토콜), Header(Host, Accept, Content-Type 등), Body 데이터를 조회.
  2. **임시 저장소 기능**: 동일한 HTTP 요청 라이프사이클 내에서 데이터 공유 (`request.setAttribute(name, value)`, `request.getAttribute(name)`).
  3. **세션 관리 기능**: `request.getSession(true)`.


### HTTP 요청 데이터를 전송하는 3가지 방식과 파싱 구현

#### 1. GET - 쿼리 파라미터

메시지 바디 없이 URL 경로 뒤에 쿼리 스트링(`?username=hello&age=20`)을 붙여 전달한다.

```java
@WebServlet(name = "requestParamServlet", urlPatterns = "/request-param")
public class RequestParamServlet extends HttpServlet {
    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        // 단일 파라미터 조회
        String username = request.getParameter("username");
        int age = Integer.parseInt(request.getParameter("age"));

        // 동일한 이름의 다중 파라미터 조회 (?username=kim&username=lee)
        String[] usernames = request.getParameterValues("username");
        
        response.getWriter().write("ok");
    }
}
```

#### 2. POST - HTML Form
웹 브라우저 폼 전송 시 `Content-Type: application/x-www-form-urlencoded` 헤더와 함께 메시지 바디에 쿼리 파라미터 형식으로 실려 전송된다.
* 서버 입장에서는 GET 쿼리 파라미터와 데이터 형식이 완전히 동일하므로, 동일하게 `request.getParameter()`를 통해 구분 없이 투명하게 조회할 수 있다.

#### 3. HTTP 메시지 바디 직접 전송 (JSON API)
HTTP API에서 주로 사용하며, `Content-Type: application/json` 형식으로 전송된다. 서블릿 입력 스트림(`ServletInputStream`)을 읽은 후 Jackson의 `ObjectMapper`를 사용하여 자바 객체로 변환한다.

```java
@Getter @Setter
public class HelloData {
    private String username;
    private int age;
}
```

```java
@WebServlet(name = "requestBodyJsonServlet", urlPatterns = "/request-body-json")
public class RequestBodyJsonServlet extends HttpServlet {
    private ObjectMapper objectMapper = new ObjectMapper();

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        ServletInputStream inputStream = request.getInputStream();
        String messageBody = StreamUtils.copyToString(inputStream, StandardCharsets.UTF_8);

        // JSON 문자열 -> Java 객체 역직렬화
        HelloData helloData = objectMapper.readValue(messageBody, HelloData.class);
        
        response.getWriter().write("ok");
    }
}
```

### HttpServletResponse와 응답 데이터 생성
서블릿은 `HttpServletResponse`를 통해 HTTP 응답 상태 코드(200, 302, 404 등), 응답 헤더(`Content-Type`, 캐시 제어, 쿠키), 리다이렉트(`response.sendRedirect()`)를 편리하게 제어한다.

* **HTML 응답**: `response.setContentType("text/html;charset=utf-8")` 지정 후 태그 출력.
* **JSON 응답**: `response.setContentType("application/json;charset=utf-8")` 지정 후 `objectMapper.writeValueAsString(data)` 출력.

## 서블릿에서 JSP, 그리고 MVC 패턴으로의 진화

### 순수 서블릿으로 화면을 개발할 때의 한계

동적 HTML을 생성하기 위해 서블릿 자바 코드 내에서 일일이 문자열 결합으로 HTML 태그를 출력해야 했다.

```java
@WebServlet(name = "memberSaveServlet", urlPatterns = "/servlet/members/save")
public class MemberSaveServlet extends HttpServlet {
    private MemberRepository memberRepository = MemberRepository.getInstance();

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        String username = request.getParameter("username");
        int age = Integer.parseInt(request.getParameter("age"));
        Member member = new Member(username, age);
        memberRepository.save(member);

        response.setContentType("text/html;charset=utf-8");
        PrintWriter w = response.getWriter();
        w.write("<html><body>성공 id=" + member.getId() + "</body></html>");
    }
}
```
* **문제점**: 자바 코드 속에 HTML 태그가 복잡하게 섞여 오타 발생 가능성이 높고 가독성이 최악이다.

### JSP의 도입과 단일 책임 원칙(SRP) 위반

HTML 문서 내부에 필요한 동적 영역에만 자바 코드를 삽입할 수 있는 템플릿 엔진(JSP)이 등장했다.

```jsp
<%@ page import="hello.servlet.domain.member.MemberRepository" %>
<%@ page import="hello.servlet.domain.member.Member" %>
<%@ page contentType="text/html;charset=UTF-8" language="java" %>
<%
    MemberRepository memberRepository = MemberRepository.getInstance();
    String username = request.getParameter("username");
    int age = Integer.parseInt(request.getParameter("age"));
    Member member = new Member(username, age);
    memberRepository.save(member);
%>
<html>
<body>
    <ul>
        <li>id=<%=member.getId()%></li>
        <li>username=<%=member.getUsername()%></li>
    </ul>
</body>
</html>
```

* **JSP의 치명적 문제점**: 상단에는 데이터베이스 저장 및 비즈니스 로직이 있고 하단에는 화면 출력 로직이 공존한다. 한 파일이 너무 많은 책임을 떠안게 되어 유지보수가 불가능해진다.
* **근본 원인 분석**: **UI를 변경하는 라이프사이클**과 **비즈니스 로직을 변경하는 라이프사이클**은 완전히 다르다. 변경 주기가 상이한 두 관심사를 한 코드에 두는 것은 유지보수성을 극도로 저해한다.

### MVC 패턴의 등장 및 적용

역할을 명확히 분리하기 위해 **MVC 패턴(Model-View-Controller)** 이 정립되었다:
* **컨트롤러(Controller)**: HTTP 요청을 받아 파라미터를 검증하고, 비즈니스 로직(서비스 계층)을 실행한 뒤 결과 데이터를 모델에 담는다.
* **모델(Model)**: 뷰에 출력할 데이터를 담아두는 보관함이다 (`HttpServletRequest`의 임시 저장소 활용).
* **뷰(View)**: 모델에 담긴 데이터를 참조하여 화면(HTML)을 그리는 작업에만 전념한다.

```java
@WebServlet(name = "mvcMemberSaveServlet", urlPatterns = "/servlet-mvc/members/save")
public class MvcMemberSaveServlet extends HttpServlet {
    private MemberRepository memberRepository = MemberRepository.getInstance();

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        String username = request.getParameter("username");
        int age = Integer.parseInt(request.getParameter("age"));
        Member member = new Member(username, age);
        memberRepository.save(member);

        // 1. Model 역할을 수행하는 request 객체에 데이터 보관
        request.setAttribute("member", member);

        // 2. View 역할을 수행하는 JSP로 내부 포워드
        String viewPath = "/WEB-INF/views/save-result.jsp";
        RequestDispatcher dispatcher = request.getRequestDispatcher(viewPath);
        dispatcher.forward(request, response);
    }
}
```

```jsp
<%@ page contentType="text/html;charset=UTF-8" language="java" %>
<html>
<body>
성공
<ul>
    <li>id=${member.id}</li>
    <li>username=${member.username}</li>
    <li>age=${member.age}</li>
</ul>
</body>
</html>
```

* **`RequestDispatcher.forward()`**: 클라이언트 브라우저를 거치지 않고 서버 내부에서 서블릿이 JSP로 제어권을 넘긴다. 클라이언트는 URL 변경을 인지하지 못한다.
* **`/WEB-INF` 디렉토리**: 브라우저에서 직접 URL을 입력하여 JSP 파일에 접근하는 것을 WAS 차원에서 차단하며, 반드시 컨트롤러 서블릿을 통해서만 포워드되도록 강제한다.

### 초기 서블릿 MVC의 구조적 한계

1. **포워딩 중복**: `RequestDispatcher dispatcher = request.getRequestDispatcher(viewPath); dispatcher.forward(request, response);` 코드가 모든 컨트롤러 서블릿마다 기계적으로 반복된다.
2. **ViewPath 경로 중복**: prefix(`/WEB-INF/views/`)와 suffix(`.jsp`)가 하드코딩되어 있어, 뷰 템플릿 변경 시 전체 컨트롤러를 일일이 수정해야 한다.
3. **불필요한 서블릿 종속성**: 사용하지 않는 `HttpServletResponse` 객체까지 주입받아야 하며, 서블릿 객체에 종속되어 단위 테스트 작성이 매우 까다롭다.
4. **공통 처리의 한계**: 인증/인가, 로깅, 예외 처리 등 모든 컨트롤러 진입 전 공통 처리를 수행할 단일 진입점이 부재한다.

이를 해결하기 위해 **프론트 컨트롤러(Front Controller) 패턴**이 필수적으로 요구된다.

## MVC 프레임워크 밑바닥부터 만들기 (Front Controller v1 ~ v5)

### v1: 프론트 컨트롤러 도입

모든 요청을 단 하나의 프론트 컨트롤러 서블릿(`FrontControllerServletV1`)이 받아 공통 진입점을 구축하고, 다형성 인터페이스를 통해 실제 컨트롤러를 호출한다.

```
[클라이언트 요청] 
      ↓
Front Controller (URL 매핑 정보 조회 -> 다형성 인터페이스 호출)
      ↓
ControllerV1 구현체 (비즈니스 로직 실행 후 직접 JSP forward)
      ↓
JSP (화면 렌더링)
```


```java
public interface ControllerV1 {
    void process(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException;
}
```

```java
@WebServlet(name = "frontControllerServletV1", urlPatterns = "/front-controller/v1/*")
public class FrontControllerServletV1 extends HttpServlet {
    private Map<String, ControllerV1> controllerMap = new HashMap<>();

    public FrontControllerServletV1() {
        controllerMap.put("/front-controller/v1/members/new-form", new MemberFormControllerV1());
        controllerMap.put("/front-controller/v1/members/save", new MemberSaveControllerV1());
        controllerMap.put("/front-controller/v1/members", new MemberListControllerV1());
    }

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        String requestURI = request.getRequestURI();
        ControllerV1 controller = controllerMap.get(requestURI);
        if (controller == null) {
            response.setStatus(HttpServletResponse.SC_NOT_FOUND);
            return;
        }
        controller.process(request, response);
    }
}
```
* **성과**: 단일 진입점이 마련되었다.
* **한계**: 개별 컨트롤러마다 포워딩(`dispatcher.forward()`) 중복 코드가 여전히 존재한다.

### v2: View 분리
컨트롤러가 직접 포워딩하지 않고, 뷰 경로를 캡슐화한 `MyView` 객체를 반환하도록 역할을 분리합니다.

```java
public class MyView {
    private String viewPath;

    public MyView(String viewPath) {
        this.viewPath = viewPath;
    }

    public void render(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        RequestDispatcher dispatcher = request.getRequestDispatcher(viewPath);
        dispatcher.forward(request, response);
    }
}
```

```java
public interface ControllerV2 {
    MyView process(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException;
}
```

* 프론트 컨트롤러가 반환받은 `MyView`의 `render()`를 일괄 호출함으로써, 컨트롤러 내부의 포워딩 중복 코드가 완전히 사라진다.

### v3: Model 추가와 서블릿 종속성 제거
컨트롤러가 서블릿 기술(`HttpServletRequest`, `HttpServletResponse`)을 전혀 알 필요가 없도록, 프론트 컨트롤러가 요청 파라미터를 순수 `Map<String, String> paramMap`으로 변환하여 넘겨줍니다. 또한 논리 뷰 이름과 모델 데이터를 함께 담는 `ModelView` 객체를 도입하고 `ViewResolver`를 추가합니다.

```java
public class ModelView {
    private String viewName; // 논리적 뷰 이름 (예: "save-result")
    private Map<String, Object> model = new HashMap<>();

    public ModelView(String viewName) {
        this.viewName = viewName;
    }
    // getter, setter
}
```

```java
public interface ControllerV3 {
    ModelView process(Map<String, String> paramMap);
}
```

```java
public class MemberSaveControllerV3 implements ControllerV3 {
    private MemberRepository memberRepository = MemberRepository.getInstance();

    @Override
    public ModelView process(Map<String, String> paramMap) {
        String username = paramMap.get("username");
        int age = Integer.parseInt(paramMap.get("age"));
        Member member = new Member(username, age);
        memberRepository.save(member);

        ModelView mv = new ModelView("save-result");
        mv.getModel().put("member", member);
        return mv;
    }
}
```

```java
// FrontControllerServletV3 내부 처리 로직
Map<String, String> paramMap = createParamMap(request);
ModelView mv = controller.process(paramMap);

String viewName = mv.getViewName();
MyView view = viewResolver(viewName); // "/WEB-INF/views/" + viewName + ".jsp"
view.render(mv.getModel(), request, response);
```

* **성과**: 컨트롤러가 순수한 POJO 자바 객체가 되어 단위 테스트가 매우 간결해졌으며, 물리 경로 중복이 뷰 리졸버를 통해 말끔히 해소되었다.

### v4: 단순하고 실용적인 컨트롤러

v3는 훌륭한 아키텍처이지만 개발자가 매번 `ModelView` 인스턴스를 생성해야 하는 사소한 번거로움이 존재한다다. v4에서는 프론트 컨트롤러가 `model` 객체를 파라미터로 넘겨주고, 컨트롤러는 오직 **논리 뷰 이름(String)만 반환**하도록 단순화한다.

```java
public interface ControllerV4 {
    String process(Map<String, String> paramMap, Map<String, Object> model);
}
```

```java
public class MemberSaveControllerV4 implements ControllerV4 {
    private MemberRepository memberRepository = MemberRepository.getInstance();

    @Override
    public String process(Map<String, String> paramMap, Map<String, Object> model) {
        String username = paramMap.get("username");
        int age = Integer.parseInt(request.getParameter("age"));
        Member member = new Member(username, age);
        memberRepository.save(member);

        model.put("member", member);
        return "save-result"; // 논리 뷰 이름 직접 반환
    }
}
```

### v5: 어댑터 패턴(Adapter Pattern) 도입과 핸들러 확장

만약 어떤 개발자는 `ControllerV3` 방식을, 어떤 개발자는 `ControllerV4` 방식을 원할 때, 완전히 규격이 다른 인터페이스들을 공존시키기 위해 **어댑터 패턴**을 적용한다. 컨트롤러의 범위를 더 넓은 개념인 **핸들러(Handler)**로 일반화한다.

```java
public interface MyHandlerAdapter {
    boolean supports(Object handler);
    ModelView handle(HttpServletRequest request, HttpServletResponse response, Object handler) 
            throws ServletException, IOException;
}
```

```java
public class ControllerV4HandlerAdapter implements MyHandlerAdapter {
    @Override
    public boolean supports(Object handler) {
        return (handler instanceof ControllerV4);
    }

    @Override
    public ModelView handle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        ControllerV4 controller = (ControllerV4) handler;
        Map<String, String> paramMap = createParamMap(request);
        Map<String, Object> model = new HashMap<>();

        String viewName = controller.process(paramMap, model);

        // 어댑터가 110V를 220V로 변환하듯 ModelView 규격에 맞추어 변환 반환
        ModelView mv = new ModelView(viewName);
        mv.setModel(model);
        return mv;
    }
}
```

```java
@WebServlet(name = "frontControllerServletV5", urlPatterns = "/front-controller/v5/*")
public class FrontControllerServletV5 extends HttpServlet {
    private final Map<String, Object> handlerMappingMap = new HashMap<>();
    private final List<MyHandlerAdapter> handlerAdapters = new ArrayList<>();

    public FrontControllerServletV5() {
        initHandlerMappingMap();
        initHandlerAdapters();
    }

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response) 
            throws ServletException, IOException {
        Object handler = getHandler(request);
        if (handler == null) {
            response.setStatus(HttpServletResponse.SC_NOT_FOUND);
            return;
        }

        MyHandlerAdapter adapter = getHandlerAdapter(handler);
        ModelView mv = adapter.handle(request, response, handler);

        MyView view = viewResolver(mv.getViewName());
        view.render(mv.getModel(), request, response);
    }

    private Object getHandler(HttpServletRequest request) {
        return handlerMappingMap.get(request.getRequestURI());
    }

    private MyHandlerAdapter getHandlerAdapter(Object handler) {
        for (MyHandlerAdapter adapter : handlerAdapters) {
            if (adapter.supports(handler)) {
                return adapter;
            }
        }
        throw new IllegalArgumentException("handler adapter를 찾을 수 없습니다. handler=" + handler);
    }
}
```

## 스프링 MVC 전체 구조와 DispatcherServlet

### 직접 만든 프레임워크 vs 스프링 MVC 1:1 매핑

| 직접 만든 컴포넌트 | 스프링 MVC 공식 컴포넌트 | 역할 및 설명 |
| :--- | :--- | :--- |
| `FrontControllerServlet` | **`DispatcherServlet`** | 스프링 MVC의 전면 프론트 컨트롤러 서블릿 |
| `handlerMappingMap` | **`HandlerMapping`** | 요청 URL을 처리할 핸들러(컨트롤러) 검색 |
| `MyHandlerAdapter` | **`HandlerAdapter`** | 핸들러를 실행할 수 있는 적절한 어댑터 검색 및 실행 |
| `ModelView` | **`ModelAndView`** | 뷰의 논리 이름과 모델 데이터를 함께 보관하는 객체 |
| `viewResolver` | **`ViewResolver`** | 논리적 뷰 이름을 실제 물리적 `View` 객체로 변환 |
| `MyView` | **`View`** | 최종 화면 렌더링(JSP 포워드, 타임리프 렌더링 등) |

### DispatcherServlet.doDispatch() 8단계 동작 흐름

`DispatcherServlet`의 부모 클래스인 `FrameworkServlet.service()`에서 시작하여 `doDispatch()`가 호출됩니다.

```
[클라이언트 HTTP 요청]
         ↓
1. 핸들러 조회: HandlerMapping 목록에서 요청을 처리할 핸들러(컨트롤러) 검색
2. 핸들러 어댑터 조회: 핸들러를 실행할 수 있는 HandlerAdapter 검색 (supports() 검사)
3. 어댑터 실행: HandlerAdapter.handle() 호출
4. 핸들러 실행: HandlerAdapter가 실제 핸들러(컨트롤러) 메서드를 실행
5. ModelAndView 반환: 핸들러의 실행 결과를 HandlerAdapter가 ModelAndView로 변환하여 반환
6. ViewResolver 호출: 논리 뷰 이름을 기반으로 ViewResolver 검색 및 실행
7. View 반환: 물리적 렌더링을 담당하는 View 객체 반환 (InternalResourceView, ThymeleafView 등)
8. 뷰 렌더링: view.render()를 호출하여 최종 HTML 또는 데이터 응답 생성
```

### 핸들러 매핑과 핸들러 어댑터의 우선순위

스프링 부트 구동 시 자동 등록되는 매핑 및 어댑터는 우선순위에 따라 순차 탐색됩니다.

```
HandlerMapping 우선순위:
0순위 = RequestMappingHandlerMapping   : @RequestMapping, @Controller 기반
1순위 = BeanNameUrlHandlerMapping      : 스프링 빈의 이름으로 핸들러 검색

HandlerAdapter 우선순위:
0순위 = RequestMappingHandlerAdapter   : @RequestMapping 기반 컨트롤러 처리
1순위 = HttpRequestHandlerAdapter      : HttpRequestHandler 인터페이스 처리
2순위 = SimpleControllerHandlerAdapter : 과거 Controller 인터페이스 처리
```
